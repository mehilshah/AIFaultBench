# recovered-from-issue: https://github.com/deepspeedai/DeepSpeed/issues/7770

TITLE
[BUG][Deepcompile] OOM during DeepCompile pre-pass eager node-by-node profiling (FX Interpreter) due to decomposed cross_entropy materializing huge intermediates

BODY
**Describe the bug**
When using DeepCompile, an OOM occurs during the pre-optimization eager, node-by-node profiling stage (FX Interpreter). The same model/input runs successfully in eager and torch.compile modes, but DeepCompile fails before optimization passes run. This effectively limits DeepCompile to training only much smaller models under the same fixed GPU memory.

**Expected behavior**
DeepCompile profiling should not introduce significantly higher peak memory than the actual training execution (eager / compiled), or it should provide a way to avoid profiling paths that materialize unrealistic intermediates.

**Actual behavior**
During profiling, the FX graph executes a decomposed sequence for nn.functional.cross_entropy that materializes a large [tokens, vocab] tensor via aten.full + aten.scatter, followed by multiple same-shaped ops. This causes extremely large temporary allocations and OOMs.

For float32, 10240 * 128256 ≈ 1.31e9 elements → ~5.25 GB for just the full() tensor. Multiple same-sized intermediates exist in this chain, so peak memory during node-by-node eager execution can easily exceed GPU capacity.

This allocation pattern does not happen (or is significantly reduced) in real training runs, since eager/compiled typically use fused/specialized implementations for cross entropy (e.g., log_softmax + NLLLoss / fused kernels).

**Impact**
DeepCompile cannot be used to train medium/large models under the same fixed GPU memory, because the profiling stage OOMs before optimization passes, even though the actual training execution is feasible.

**Questions**
Is it expected that DeepCompile performs eager node-by-node profiling on decomposed graphs that may materialize extremely large intermediates?
