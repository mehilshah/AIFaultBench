### 🐛 Describe the bug

The FlashInfer fused allreduce + residual RMSNorm + static quantization
patterns can match graphs where the allreduce/RMSNorm input is BF16 but the
RMSNorm weight is FP32.

This causes silently corrupted generation with
`nvidia/Qwen3.6-27B-NVFP4` at tensor parallel size 4 on H100 GPUs. A
deterministic prompt produces repeated exclamation marks instead of `OK`.

The affected patterns are:

- `AllReduceFusedAddRMSNormStaticQuantFP8Pattern`
- `AllReduceFusedAddRMSNormStaticQuantNVFP4Pattern`

These residual quantized patterns do not apply
`_norm_input_weight_dtype_match`, although the corresponding non-residual
quantized patterns and ordinary residual RMSNorm patterns perform this
compatibility check.

Qwen/Gemma-style RMSNorm is relevant because its effective weight is computed
using an expression such as:

```python
weight.float() + 1.0
```

The residual stream and allreduce input are BF16, while the effective RMSNorm
weight passed by the matched graph is FP32. The fused quantized FlashInfer
operation is therefore selected with incompatible input and norm-weight
dtypes.

This is a silent correctness failure: the server starts normally and returns
successful HTTP responses containing corrupted tokens.

## Reproduction

Hardware:

- 4× NVIDIA H100
- Tensor parallel size 4
- No NVSwitch; FlashInfer TRT-LLM allreduce backend

Software configurations in which the failure was reproduced:

- vLLM 0.24.0
- PyTorch 2.11.0+cu130
- FlashInfer 0.6.12
- vLLM main at `e5588e49b`
- FlashInfer 0.6.13
- CUDA 13.0

Start the server:

```bash

export VLLM_FLASHINFER_ALLREDUCE_BACKEND=trtllm

vllm serve nvidia/Qwen3.6-27B-NVFP4 \
```

## Isolation

| Configuration | Result |
|---|---|
| TP=1 | Correct |
| TP=4 with the default allreduce/RMSNorm fusion | Corrupted |
| TP=4 with `--enforce-eager` | Correct |
| TP=4 with `-cc.pass_config.fuse_allreduce_rms=False` | Correct |
| TP=4 with only the quantized allreduce/RMSNorm fusion patterns disabled | Correct |
| TP=4 with CUDA graphs disabled but the fusion retained | Corrupted |
| TP=4 with PDL disabled but the fusion retained | Corrupted |
| TP=4 with two-shot allreduce used for prefill | Corrupted |

This indicates that the failure is not caused by CUDA graph replay, PDL
ordering, or the one-shot prefill path.

Disabling only the quantized allreduce/RMSNorm patterns restores correct
generation while leaving the ordinary allreduce + RMSNorm fusion enabled.

Compiled FX graph inspection shows the residual static-FP8 fusion pattern
matching with:

- BF16 allreduce/RMSNorm input
- FP32 Qwen/Gemma RMSNorm weight

## Proposed fix

Apply the existing compatibility check to both residual quantized pattern
registrations:

```python
extra_check=_norm_input_weight_dtype_match
```

Specifically:

```text
AllReduceFusedAddRMSNormStaticQuantFP8Pattern
AllReduceFusedAddRMSNormStaticQuantNVFP4Pattern
```

With these guards, mixed-dtype Qwen/Gemma graphs no longer select the unsafe
allreduce + RMSNorm + quant fusion. They can still select the specialized
allreduce + Gemma RMSNorm fusion using `weight_bias=1.0`, followed by separate
quantization.

Models whose RMSNorm input and weight have compatible dtypes retain the fully
fused quantized path.

## Validation

After adding the two guards:

- The full Qwen server returns exactly `"OK"`.
- Normal CUDA graph operation remains enabled.
- PDL remains enabled.
- The ordinary optimized allreduce + Gemma RMSNorm fusion remains active.
- Focused distributed regression tests pass for both RMS custom-op modes.

Test result:

```text
2 passed, 32 deselected
```

Test command:

```bash

  -k "GemmaRMSNormStaticQuantFP8 and trtllm" \

```

The regression test uses:

- FlashInfer TRT-LLM allreduce backend

## Additional context

The quantized fusion patterns were introduced in
https://github.com/vllm-project/vllm/pull/21069.

I found related reports with repeated-token output, but none that identify this
specific mixed-dtype allreduce/RMSNorm/quant fusion problem:

- https://github.com/vllm-project/vllm/issues/27364 uses TP=1, so it cannot
  involve this allreduce fusion.
- https://huggingface.co/nvidia/Qwen3.6-27B-NVFP4/discussions/4 reports a
  similar visible symptom on Blackwell, but its hardware and version behavior
  differ from this H100 TP=4 reproducer.
