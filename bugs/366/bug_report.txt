# [Bug]: Cannot serve a Qwen3-VL sequence classification model with `num_labels > 2` (multi-label classification)


The trained checkpoint's `config.json` contains:

```json
{
  "architectures": ["Qwen3VLForConditionalGeneration"],
  "model_type": "qwen3_vl",
  "problem_type": "multi_label_classification",
  "id2label": { "0": "LABEL_0", "...": "...", "19": "LABEL_19" },
  "label2id": { "LABEL_0": 0, "...": "...", "LABEL_19": 19 }
}
```

## 🐛 Describe the bug

I trained a **Qwen3-VL-8B** model for **multi-label sequence classification** (`num_labels=20`, `problem_type=multi_label_classification`) using ms-swift. The resulting checkpoint has a standard classification head `score.weight` of shape `[20, 4096]`.

I cannot serve this model with `vllm serve` for the `classify` task. I tried all three plausible ways to launch it, and each fails for a different reason. The root cause appears to be that vLLM currently has **no code path that loads a Qwen3-VL sequence-classification head with an arbitrary `num_labels`** — the only available `Qwen3VLForSequenceClassification` implementation is hardcoded for the **Qwen3-VL-Reranker** case (binary, 2 classes via `classifier_from_token=["no","yes"]`).

### Attempt 1 — override architecture to `Qwen3VLForSequenceClassification`

```bash
vllm serve ../checkpoint-400/ \
  --runner pooling \
  --max-model-len 8192 \
  --limit-mm-per-prompt.image 1 \
  --hf-overrides '{"architectures": ["Qwen3VLForSequenceClassification"], "problem_type": "multi_label_classification"}'
```

Fails with a weight shape mismatch — vLLM builds a **2-class** head (reranker style) instead of reading `num_labels=20` from the config:

```text
File ".../vllm/model_executor/layers/linear.py", line 372, in weight_loader
    assert param.size() == loaded_weight.size(), (
AssertionError: Tried to load weights of size torch.Size([20, 4096])
                to a parameter of size torch.Size([2, 4096])
```

### Attempt 2 — do NOT override architecture (rely on `--runner pooling` only)

```bash
vllm serve ../checkpoint-400/ \
  --runner pooling \
  --max-model-len 8192 \
  --limit-mm-per-prompt.image 1 \
  --hf-overrides '{"problem_type": "multi_label_classification"}'
```

vLLM falls back to loading the model as `Qwen3VLForEmbedding`, which has **no classification head**, so the `score` weights cannot be placed:

```text
File ".../vllm/model_executor/models/utils.py", line 324, in _load_module
    raise ValueError(msg)
ValueError: There is no module or parameter named 'score' in Qwen3VLForEmbedding.
```

### Attempt 3 — keep the config's generative architecture

Keeping `Qwen3VLForConditionalGeneration` (the value in the checkpoint's `config.json`) loads the model as a generative model, so the `/classify` endpoint is not usable at all.

## Expected behavior

`vllm serve` should be able to load a Qwen3-VL sequence-classification checkpoint with an arbitrary `num_labels` (here 20) and a standard `score` head of shape `[num_labels, hidden_size]`, and expose the `/classify` endpoint returning a per-label probability vector (sigmoid for `multi_label_classification`, softmax for `single_label_classification`), consistent with how text-only `*ForSequenceClassification` models are handled.

## Root cause (analysis)

- The `id2label` / `label2id` in the config already encode 20 labels, so `num_labels` is not missing.
- However, vLLM's `Qwen3VLForSequenceClassification` seems to be implemented specifically for the **Qwen3-VL-Reranker**, deriving the classification head dimension from `classifier_from_token` (2 tokens → 2 classes) rather than from `num_labels` / `id2label`. Therefore it ignores `num_labels=20` and builds a `[2, 4096]` head.
- Without the architecture override, the pooling runner defaults to `Qwen3VLForEmbedding`, which has no `score` head at all.

So there is currently **no way** to serve a general N-class (multi-label) Qwen3-VL classification model in vLLM.

## Request

Please add support for loading Qwen3-VL (and ideally Qwen2.5-VL) sequence-classification models with an arbitrary `num_labels` and a standard `score` head, honoring `problem_type` (`multi_label_classification` → sigmoid, `single_label_classification` → softmax), the same way text-only `*ForSequenceClassification` models already work.

## Workaround (for others hitting this)

Using the PyTorch (`pt`) backend works correctly, because HF-native loading respects the real `[20, 4096]` head:

```python
from swift.llm import PtEngine
engine = PtEngine(model_path, task_type='seq_cls',
                  num_labels=20, problem_type='multi_label_classification')
```

or `swift deploy --infer_backend pt`. Only the vLLM backend is affected.
