### Reproduction Steps / Example Code (Python)

```python
from langchain_perplexity import ChatPerplexity
from langchain_core.messages import AIMessage, ToolMessage

llm = ChatPerplexity(model="sonar", api_key="dummy")

# 1) AIMessage.tool_calls are silently dropped on serialization:
ai = AIMessage(
    content="",
    tool_calls=[{"id": "call_1", "name": "search", "args": {"q": "x"}, "type": "tool_call"}],
)
print(llm._convert_message_to_dict(ai))
# -> {'role': 'assistant', 'content': ''}   # note: tool_calls is gone

# 2) A ToolMessage cannot be serialized at all:
llm._convert_message_to_dict(ToolMessage(content="result", tool_call_id="call_1"))
# raises TypeError
```

### Description

`ChatPerplexity._convert_message_to_dict` (chat_models.py:772-783) only handles ChatMessage / SystemMessage / HumanMessage / AIMessage. It has no `ToolMessage` branch (falls through to `raise TypeError("Got unknown type ...")`), and its `AIMessage` branch builds `{"role": "assistant", "content": ...}` without serializing `.tool_calls`.

The inverse path, `_convert_delta_to_message_chunk` (chat_models.py:947), already deserializes `role: "tool"` chunks into `ToolMessageChunk`. So the integration can receive tool messages but cannot send them. As a result, any `ToolMessage` round-tripped through `ChatPerplexity` -- a client-side tool-calling loop, or a shared message history across providers via `RunnableWithFallbacks` -- raises `TypeError` on the next turn, and an assistant turn's `tool_calls` are dropped.

`langchain-openai`'s `_convert_message_to_dict` handles both cases (serializes `tool_calls`/`invalid_tool_calls`, sets `content` to None when tool_calls are present, and has a `tool`-role branch). The perplexity converter should match.
