### 🐛 Describe the bug

On **gfx942 (MI300X)**, serving `zai-org/GLM-5.1-FP8` with **MTP speculative decoding** under
**torch.compile / CUDA-graph** intermittently crashes the engine with a GPU memory access fault:

```text
Memory access fault by GPU node-N (Agent handle: ...) on address 0x... . Reason: Unknown.
... Worker proc VllmWorker-N died unexpectedly ...
vllm.v1.engine.exceptions.EngineDeadError
```

**Only `--enforce-eager` (cudagraph=NONE) is immune** — the crash occurs in both
`FULL_AND_PIECEWISE` and `PIECEWISE`.

### Reproduce

```bash
VLLM_ROCM_USE_AITER=1 vllm serve zai-org/GLM-5.1-FP8 \
  --tensor-parallel-size 8 --block-size 1 --kv-cache-dtype fp8 \
  --max-model-len 200000 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":2}'
# Send a few ~8K-token requests at concurrency 1.
```

Containerized launch we used (public base image + the still-unmerged #45324 sparse-attn
masking patch applied on top):

```bash
# Base: vllm/vllm-openai-rocm:v0.23.0 + #45324 applied on top
docker run -d --name glm5_server \
  --device /dev/kfd --device /dev/dri --group-add video --group-add render \
  --ipc host --network host -v $CACHE_DIR:/model \
  -e VLLM_ROCM_USE_AITER=1 -e HIP_FORCE_DEV_KERNARG=1 -e NCCL_MIN_NCHANNELS=112 \
  -e TORCH_BLAS_PREFER_HIPBLASLT=1 -e PYTORCH_HIP_ALLOC_CONF=expandable_segments:True \
  -e HF_HOME=/model -e HF_HUB_OFFLINE=1 -e TRANSFORMERS_OFFLINE=1 \
  vllm/vllm-openai-rocm:v0.23.0 \
  --model zai-org/GLM-5.1-FP8 --tensor-parallel-size 8 --block-size 1 \
  --kv-cache-dtype fp8 --max-model-len 200000 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":2}'
```

### Root cause

In `vllm/v1/attention/backends/mla/rocm_aiter_mla_sparse.py`, the sparse-MLA backend uses
persistent work-split metadata buffers (`_mla_work_*`) that are allocated once and reused. They
are **written host-asynchronously in `build()` by `get_mla_metadata_v1(...)` outside the captured
graph**, but **read by the decode kernel inside the captured CUDA graph**. With no ordering
between the write and the graph replay, the kernel can read stale/partially-written metadata and
go out of bounds → GPU memory fault. Evidence: serializing kernels (`AMD_SERIALIZE_KERNEL=3`)
avoids the crash for n=1/n=3, and `work_indptr` values are in-bounds at the fault — i.e. an
ordering/race, not bad metadata values. Eager is immune because it uses dynamic per-call buffers.

### Fix

A one-line current-stream host sync in `build()` (after the metadata recompute) that orders the
write before the graph-captured read eliminates the crash; it is performance-neutral (it runs
before the heavy forward, waiting only on the tiny metadata write). Validated across 100+
requests at n=2/n=3 with fault=0 and unchanged TPOT. **I will open a PR with this fix.**
