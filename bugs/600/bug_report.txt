### 🐛 Describe the bug

## Summary

vLLM's Gemma4 video path produces **different `prompt_token_ids`** than HuggingFace Transformers' official `Gemma4Processor` for the same video input. The mismatch is visible on the **timestamp strings** embedded in the prompt (e.g. `00:00` vs `00:03` on the 2nd frame) and can also affect soft-token counts because vLLM uses a different processing pipeline than Transformers.

---

## 1. How Transformers handles Gemma4 video

Reference: huggingface/transformers(`5.12.0`).

### 1.1 Decode & sample

- Video URL/path → `BaseVideoProcessor.fetch_videos()` → **`torchcodec`** (fallback: deprecated `torchvision`).
- Returns sampled frame tensor + `VideoMetadata` (`fps`, `timestamps`, `frames_indices`, …).

[`video_processing_utils.py#L820-L838`](https://github.com/huggingface/transformers/blob/v5.12.1/src/transformers/video_processing_utils.py#L820-L838)

### 1.2 Feature extraction

- Frames go through **`Gemma4VideoProcessor._preprocess`** as a **4D video tensor** `(T, C, H, W)` — **not** per-frame image processing.
- `max_soft_tokens=70` (video default), `patch_size`, `pooling_kernel_size=3`.
- Produces `pixel_values_videos`, `video_position_ids`, and **`num_soft_tokens_per_video`**:

[`video_processing_gemma4.py#L268-L269`](https://github.com/huggingface/transformers/blob/v5.12.1/src/transformers/models/gemma4/video_processing_gemma4.py#L268-L269)

**Important:** `num_soft_tokens_per_video` holds **one** value per video, and that single value is reused for **every** frame when expanding the prompt (see 1.3).

### 1.3 Prompt expansion

[`processing_gemma4.py#L173-L190`](https://github.com/huggingface/transformers/blob/v5.12.1/src/transformers/models/gemma4/processing_gemma4.py#L173-L190)

- Timestamps come from **`metadata.timestamps`** (seconds), derived from the decoder's real fps and sampled frame indices.
- `num_soft_tokens` is a **single scalar** per video, applied to **every** frame (`self.video_token * num_soft_tokens`).
- Example on `baby.mp4` (32 frames): `fps=25`, first timestamps ≈ `00:00, 00:00, 00:00, 00:00, 00:01, …`.
- Per-frame soft tokens: **66** for all frames in our test video.

## 2. How vLLM handles Gemma4 video

Reference: `vllm-project/vllm` @ [`v0.23.0`](https://github.com/vllm-project/vllm/tree/v0.23.0) (`91df0fad4dc98a67c7659d9dbd915245d5c43d96`).

Entry: `Gemma4MultiModalProcessor._call_hf_processor` custom video branch.

### 2.1 Pre-decode

Rollout templates typically pre-decode with OpenCV before passing to vLLM:

- [`video_to_ndarrays`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/assets/video.py#L39-L68) — cv2 linspace frame sampling
- [`video_get_metadata`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/assets/video.py#L76-L100) — metadata dict consumed by the processor

Input to vLLM processor: `[(ndarray, metadata_dict), …]`.

### 2.2 vLLM processor path (differs from Transformers)

[`gemma4_mm.py#L583-L659`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/model_executor/models/gemma4_mm.py#L583-L659)

1. **Splits video into PIL frames** and runs **`Gemma4ImageProcessor` per frame** via `_call_hf_processor(..., mm_data={"images": frames})` with `max_soft_tokens=70` ([`L616-L627`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/model_executor/models/gemma4_mm.py#L616-L627)).
2. Computes **per-frame** soft-token counts via [`_compute_num_soft_tokens`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/model_executor/models/gemma4_mm.py#L274-L309) (image sizing math), **not** `Gemma4VideoProcessor`'s patch pipeline ([`L638-L645`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/model_executor/models/gemma4_mm.py#L638-L645)).
3. Builds prompt replacement with **per-frame** `n` ([`L651-L658`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/model_executor/models/gemma4_mm.py#L651-L658)), unlike Transformers' single `num_soft_tokens` for all frames.

```python
# gemma4_mm.py L611-L614, L638-L658
fps = metadata.get("fps") or 24
frame_indices = metadata.get("frames_indices", list(range(len(frames))))
timestamps = [idx / fps for idx in frame_indices]
...
n = self.info._compute_num_soft_tokens(w, h, max_soft_tokens=_VIDEO_MAX_SOFT_TOKENS)
replacement = " ".join(
    f"{t} {processor.boi_token}{processor.video_token * n}{processor.eoi_token}"
    for t, n in zip(ts_strs, num_soft_per_frame)
)
```

### 2.3 Broken metadata in `video_get_metadata`

[`video.py#L90-L99`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/assets/video.py#L90-L99)

```python
# video.py L90-L99 (video_get_metadata)
metadata = {
    "total_num_frames": num_frames,
    "fps": duration / num_frames,          # NOT the video's real fps
    "duration": duration,
    "video_backend": "opencv",
    "frames_indices": list(range(num_frames)),  # NOT linspace indices from video_to_ndarrays
    "do_sample_frames": num_frames == total_frames,
}
```

Note: `video_to_ndarrays` samples with **linspace** ([`L50`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/assets/video.py#L50)), but `video_get_metadata` reports `frames_indices = [0, 1, …, num_frames-1]` — the two helpers are **inconsistent**.

For `baby.mp4` (32 sampled frames, real fps≈25):

| Field | Transformers | vLLM `video_get_metadata` |
|-------|--------------|---------------------------|
| `fps` | `25` | `duration/32 ≈ 0.304` |
| `frames_indices` | linspace into source (e.g. `[0, 7, 15, …]`) | `[0, 1, 2, …, 31]` |
| 2nd frame timestamp | `00:00` | `1 / 0.304 ≈ 3.3s` → **`00:03`** |

This is the **first visible token diff** in our repro (decode around diff index 83: `'0'` vs `'3'` inside `00:00` vs `00:03`).

## 3. Why they don't match

| Aspect | Transformers (official) | vLLM |
|--------|----------------------|------|
| Processor | `Gemma4VideoProcessor` on 4D tensor | Per-frame `Gemma4ImageProcessor` |
| Decoder | torchcodec (URL) | OpenCV pre-decode in template |
| Soft tokens / frame | **Same** `n_tokens` for all frames (from video patches) | **Per-frame** `_compute_num_soft_tokens` |
| Timestamps | `metadata.timestamps` from decoder | `idx / (duration/num_frames)` with wrong `idx` |
| Prompt length (video-only) | 2399 tokens (`baby.mp4`) | Same chat-wrapped length (2412) but **token content differs** |

### 4.2 Show vLLM metadata bug in isolation

from vllm.assets.video import video_to_ndarrays, video_get_metadata

VIDEO = "https://modelscope-open.oss-cn-hangzhou.aliyuncs.com/images/baby.mp4"

### 4.3 vLLM processor vs HF (prompt tokens)

```python
import copy
from transformers import AutoProcessor
from vllm.config import ModelConfig
from vllm.multimodal import MULTIMODAL_REGISTRY
from vllm.assets.video import video_to_ndarrays, video_get_metadata

VIDEO = "https://modelscope-open.oss-cn-hangzhou.aliyuncs.com/images/baby.mp4"
MODEL = "google/gemma-4-E2B-it"

proc = AutoProcessor.from_pretrained(MODEL, trust_remote_code=True)
ids_hf = proc(text="<|video|>", videos=VIDEO, return_tensors="pt", add_special_tokens=False)["input_ids"][0].tolist()

# Simulate vLLM rollout input (pre-decoded tuple)
nf = proc.video_processor.num_frames
vd = video_to_ndarrays(VIDEO, nf)
meta = video_get_metadata(VIDEO, nf)

model_config = ModelConfig(MODEL, trust_remote_code=True, dtype="auto", seed=0)
vllm_proc = MULTIMODAL_REGISTRY.create_processor(model_config)
mm_items = vllm_proc.info.parse_mm_data({"video": [(vd, meta)]})

# Minimal prompt with one <|video|> placeholder (match template vllm mode)
video_token_id = proc.tokenizer.convert_tokens_to_ids("<|video|>")
prompt_ids = [video_token_id]

result = vllm_proc(prompt_ids, mm_items=mm_items, hf_processor_mm_kwargs={})
ids_vllm = result["prompt_token_ids"]

print("HF len:", len(ids_hf), "vLLM len:", len(ids_vllm))
for i, (a, b) in enumerate(zip(ids_hf, ids_vllm)):
    if a != b:
        print(f"first diff @ {i}: {a} vs {b}")
        print("HF decode:", proc.tokenizer.decode(ids_hf[max(0,i-8):i+12]))
        print("vLLM decode:", proc.tokenizer.decode(ids_vllm[max(0,i-8):i+12]))
        break
```

## 5. Impact

- GRPO/OPD train–rollout **prompt misalignment** for Gemma4 video: model trains on HF token layout but rollouts with different timestamps (and potentially different soft-token counts).
- Comment at [`gemma4_mm.py#L584-L586`](https://github.com/vllm-project/vllm/blob/v0.23.0/vllm/model_executor/models/gemma4_mm.py#L584-L586) is misleading; downstream integrators assume Transformers parity.
