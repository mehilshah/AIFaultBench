### 🐛 Describe the bug

## Bug
Sending `"parallel_tool_calls": null` to the Responses API (`/v1/responses`)
causes an unhandled `ValidationError` inside `from_request()`, returning a
500 Internal Server Error instead of a clean 422.

## Root Cause
`ResponsesRequest` accepts `null` (field is `bool | None = True`), but
`from_request()` passes the value directly to `ResponsesResponse` which
declares `parallel_tool_calls: bool` — non-optional, no default. Pydantic
v2 does not coerce `None → bool`, so it crashes.

## Reproduction (no server needed — pure Pydantic)

```python
import sys; sys.path.insert(0, '.')
from pydantic import ValidationError
from vllm.entrypoints.openai.responses.protocol import ResponsesResponse

try:
    ResponsesResponse.model_validate({
        'id': 'resp_test',
        'model': 'test-model',
        'parallel_tool_calls': None,
        'output': [],
        'status': 'completed',
    })
    print('no error')
except ValidationError as e:
    print('CRASH:', e)

# Output:
# CRASH: 1 validation error for ResponsesResponse
# parallel_tool_calls
#   Input should be a valid boolean [type=bool_type, input_value=None]
```

## Expected Behavior
`null` should resolve to the documented default (`true`), consistent with
how PR #44955 fixed the same issue in the ChatCompletion path.

## Note: distinct from PR #44955
PR #44955 fixed `parallel_tool_calls: null` behavior in `tool_calls_utils.py`
(ChatCompletion path only). The Responses API never calls that function —
confirmed via grep across all of `vllm/entrypoints/openai/responses/`.
This crash is in `from_request()` in `responses/protocol.py`, a completely
separate code path.
