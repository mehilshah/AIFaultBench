# recovered-from-issue: https://github.com/Lightning-AI/pytorch-lightning/issues/21757

TITLE
`LearningRateFinder` fails due to missing `weights_only` parameter in checkpoint restore

BODY
### Bug description

  ## Summary
`LearningRateFinder` fails when restoring its internally created temporary checkpoint because it does not expose or forward a `weights_only` parameter.  
Since PyTorch ≥ 2.6 defaults to `weights_only=True` for `torch.load`, Lightning attempts a *weights‑only* load on a checkpoint that contains full module objects, causing an `UnpicklingError`.

Manual checkpoint loading works correctly when `weights_only=False` is explicitly passed.

This makes `lr_find()` unusable for any model whose checkpoint includes non‑trivial Python objects (e.g., custom modules).

---

 ## Environment
- PyTorch: 2.12.x
- Lightning: 2.4.x
- Python: 3.11
- OS: Windows (Jupyter environment)

---

## Minimal Reproducible Example

```python
import torch
from torch import nn
from torch.utils.data import DataLoader, TensorDataset
import lightning as L

# Simple torch Module
class TorchCoder(nn.Module):
    def __init__(self, in_features, out_features):
        super().__init__()
        self.net = nn.Linear(in_features, out_features)

    def forward(self, x):
        return self.net(x)

# Simple model
class SimpleModel(L.LightningModule):
    def __init__(self, coder, loss, lr=1e-3):
        super().__init__()
        self.save_hyperparameters()
        self.layer = nn.Linear(4, 2)
        self.loss= loss
        self.lr=lr

    def training_step(self, batch, batch_idx):
        x, y = batch
        y_hat = self.layer(x)
        loss = nn.functional.mse_loss(y_hat, y)
        return loss

    def configure_optimizers(self):
        return torch.optim.Adam(self.parameters(), lr=self.lr)

# Dummy data
x = torch.randn(16, 4)
y = torch.randn(16, 2)
loader = DataLoader(TensorDataset(x, y), batch_size=4)

model = SimpleModel(
    TorchCoder(4, 2),
    loss=nn.MSELoss(),
)

trainer = L.Trainer(
    default_root_dir="lightning_logs",
    max_epochs=1,
    logger=False,
    enable_checkpointing=True,
)

# This should NOT raise an exception after the fix
lr_finder = L.pytorch.tuner.Tuner(trainer).lr_find(
    model,
    train_dataloaders=loader,
)
```

Key points:
1. Train a simple LightningModule (autoencoder).
2. Save checkpoint → loads fine with `weights_only=False`.
3. Call `trainer.tuner.lr_find(model, ...)` → fails.

---

 ## Error

```
UnpicklingError: Unsupported global: GLOBAL 'main.LitEncoder'
```


Lightning logs also show:

```
Weights only load failed... Unsupported global...
```


This happens because LR Finder internally calls:

```python
trainer._checkpoint_connector.restore(ckpt_path)
```

without specifying `weights_only=False`.

---

 ## Root Cause
 
In `lightning/pytorch/tuner/lr_finder.py`:

```python
trainer._checkpoint_connector.restore(ckpt_path)
```

This implicitly triggers a *weights‑only* load under PyTorch 2.6, which is incompatible with checkpoints containing full module objects.

Manual loading works:

```python
LitAutoEncoder.load_from_checkpoint(path, weights_only=False)
```

---

 ## Proposed Fix
 
Expose and propagate a `weights_only` parameter through the LR Finder call chain:

- `Tuner.lr_find(...)`

- `LearningRateFinder.__init__(...)`

- `LearningRateFinder.lr_find(...)`

- `_lr_find(...)`

- `trainer._checkpoint_connector.restore(ckpt_path, weights_only=...)`

Default should remain `weights_only: Optional[bool] = None` for backward compatibility.

---

 ## Why this matters
 
- LR Finder becomes unusable for many real‑world models.

- PyTorch 2.6’s new safe‑globals behavior makes implicit weights‑only loading unsafe.

- Lightning already supports full checkpoint loading elsewhere; LR Finder should be consistent.

---

 ## Request
 
Please consider:

- Adding a `weights_only` parameter to LR Finder.

- Defaulting it to `None` for backward compatibility.

- Propagating it through the LR Finder call chain.

I will open a PR with the fix (already prepared locally).
