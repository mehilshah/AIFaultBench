# Reproduction Trajectory — Bug 757: smolagents

- **Bug report:** [https://github.com/huggingface/smolagents/issues/1689](https://github.com/huggingface/smolagents/issues/1689)
- **Repository:** huggingface/smolagents @ `c035a10e991408f2ccf49fe1cfcfaf0d9a34b011`
- **Outcome:**  Not reproduced on the reference machine

## How the bug was reproduced

1. Read the issue report and its maintainer comments, which attribute the 400 response to a vLLM bug fixed by vllm-project/vllm#23318.
2. Ran `bash setup_codebase.sh` and verified the checkout was at `c035a10e991408f2ccf49fe1cfcfaf0d9a34b011`.
3. Created the isolated environment and installed the checkout editable with `bash setup_env.sh`.
4. Ran `CodeAgent` against a local fake OpenAI-compatible client that raises the exact upstream vLLM 400. The fake performs no network I/O and is used solely to verify smolagents' exception boundary.
5. Ran `bash run_repro.sh` and captured its output.

## Observed behavior

- The pinned `CodeAgent` wrapped the injected client exception as `AgentGenerationError` and preserved `Expected 2 output messages (reasoning and final), but got 64.` in its message.
- The final probe printed `NOT_REPRODUCED: smolagents wrapped the injected upstream vLLM 400; it did not create it.` and exited 0.

Full output is captured in [`repro_stdout.log`](./repro_stdout.log) and [`repro_stderr.log`](./repro_stderr.log).

## Commands

```bash
bash setup_codebase.sh      # clone the repository at the buggy commit
bash run_repro.sh
```

## Why it does not reproduce on the reference machine

The issue's 400 is generated by an affected vLLM server, rather than by smolagents. The report provides neither the affected vLLM build nor a served model/configuration, and a real model-serving environment is disallowed by this benchmark's no-live-provider rule. The local check verifies the only executable smolagents behavior: it wraps the upstream error.
