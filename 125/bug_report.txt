Title: [Bug]: collect_rollouts allows num_timesteps to exceed total_timesteps
Date: 2025-09-10T15:42:24+00:00
URL: https://github.com/DLR-RM/stable-baselines3/issues/2175

Description:
### 🐛 Bug

When using OnPolicyAlgorithm.collect_rollouts (e.g. with PPO), the agent may perform more environment steps than specified by the total_timesteps argument.

For example, with:

>   num_envs = 15
>   total_timesteps = 10000
>   n_steps = 10001

the algorithm increments timesteps in multiples of num_envs, and because n_steps is not validated against total_timesteps, self.num_timesteps can exceed 10,000 (e.g., 10,015).

Also there is no assert to validate that n_rollout_steps <= total_timesteps, so the loop inside collect_rollout can continue to perform more time steps than total_timesteps (assuming n_rollout_steps > total_timesteps).

This is problematic because when a user sets total_timesteps = 10000, they expect training to stop exactly at that value. However, the stopping condition is only checked in the outer learn() loop and not enforced inside collect_rollouts, so overshooting is possible.

### To Reproduce

```python
import gymnasium as gym
from stable_baselines3 import PPO
from stable_baselines3.common.vec_env import DummyVecEnv

def make_env():
    return gym.make("CartPole-v1")

# 15 parallel environments
num_envs = 15
env = DummyVecEnv([make_env for _ in range(num_envs)])

# n_steps deliberately larger than total_timesteps
model = PPO("MlpPolicy", env, n_steps=10001, verbose=1)

# total_timesteps = 10_000
model.learn(total_timesteps=10_000)

print("Final num_timesteps:", model.num_timesteps)
```
